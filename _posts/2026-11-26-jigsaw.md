**TL;DR:** Your model on high-resolution scientific data runs out of GPU memory, even with a batch size of one? **Jigsaw** distributes the model *and* each sample across GPUs, so you can train larger models on larger inputs than fit on a single GPU. Adding GPUs adds memory, without rewriting your model or your training loop.

Large models for scientific data are not language models. Text is compact: a sentence is a short list of tokens, and each token carries a lot of information. Scientific inputs are high-resolution 2D or 3D images with many physical variables at every point, and a single sample can be a gigabyte or more. One sample becomes hundreds of thousands to millions of tokens, and memory is dominated by activations rather than weights. Parallelism tools built for language models split the sequence or the weights, but every GPU still holds the full channel dimension of its part of the input. Jigsaw is a PyTorch library that splits the image into tiles *and* the channels and weights into shards, so no GPU holds a full copy of the input, the activations or the model. You swap in Jigsaw layers, or let a converter do it, and keep a plain PyTorch training loop. The same model code runs on a laptop CPU, NVIDIA GPUs and AMD GPUs.

* **67 million tokens** in a single attention layer on 1,024 GH200 GPUs, at a constant memory per GPU.
* **Runs on NVIDIA and AMD.** Tested on NVIDIA A100, GH200 and GB200, and on AMD MI250X, with no code changes.
* **Plain PyTorch.** Your optimizer, autograd, `torch.autocast` and `DistributedDataParallel` work as before.

## Scientific models are not language models

A vision transformer cuts an image into patches and treats each patch as a token. The number of tokens grows with the image area. For everyday photos this is a few hundred tokens. For scientific data it is far larger.

Take global weather data. ERA5 at 0.25° resolution is a 721 × 1440 grid, about a million points per variable, with 84 variables. With 4 × 4 patches, a global-attention ViT sees 64,800 tokens. With 2 × 2 patches it sees 259,200. The finer view pays off: in our experiments, the 2 × 2 model reached the same validation loss in 1.4× fewer training steps.

These workloads differ from language models in almost every respect:

| | Language models | Scientific vision models |
|---|---|---|
| Input | Token IDs, looked up in an embedding table | Dense physical fields: 84 variables at every grid point |
| Sequence length | Thousands of tokens; very long contexts are the exception | Every sample: 64,800 tokens to millions |
| Structure | A 1D sequence | A 2D or 3D grid where neighbors matter: convolutions, windowed and shifted-window attention |
| Parameters | Billions to trillions | Hundreds of millions to a few billion |
| Memory | Weights and optimizer state are a large share | Activations of a single sample dominate |
| Batch size | Millions of tokens per step | A few samples per step; for weather models, quality degrades beyond about 16 to 32 |

This changes which kind of parallelism helps:

* **Splitting only the weights** (FSDP, ZeRO, Megatron-style tensor parallelism) does not help when the activations of one sample do not fit on a GPU.
* **Splitting only the sequence** (context parallelism) leaves the full channel dimension on every GPU. With 84 input variables and wide embeddings, that is a large, redundant copy.
* **Data parallelism** is limited by the small batch size.
* **Spatial operations**, such as convolutions and shifted windows, need GPUs holding neighboring tiles to exchange their boundary regions. Libraries built for 1D token sequences do not provide this.

### And TransformerEngine?

[TransformerEngine](https://github.com/NVIDIA/TransformerEngine) is NVIDIA's library of fused transformer kernels: attention, fused layer norm and linear layers, and FP8. It makes the computation on each GPU fast. Its parallel features follow the language-model layout, with tensor parallelism over the weights and context parallelism over the sequence. It has no concept of an image tile: no halo exchange for convolutions or shifted windows, and no split of the input channels.

Jigsaw works one level above this. It decides which part of the image, the channels and the weights each GPU holds, and how the GPUs communicate. Inside each GPU it can call TransformerEngine: with `attn_backend="te"`, Jigsaw's distributed attention uses TransformerEngine's fused cuDNN attention on Hopper and newer GPUs, and the flash-attention kernel on older GPUs and on AMD. Without TransformerEngine installed, Jigsaw uses PyTorch's `scaled_dot_product_attention`.

## How Jigsaw splits the work

Jigsaw uses a two-axis process mesh:

* **Domain axis:** the image, or the token sequence, is split into tiles. Each GPU holds one tile. Convolutions exchange the boundary pixels (halos) with neighboring tiles. Attention passes keys and values around the ring of tiles, so every token still attends to the whole image.
* **Tensor axis:** the channels of the input and the weights of each layer are split. Attention heads are split along this axis as well.

Each layer is written as a distributed matrix multiplication that takes sharded inputs and produces sharded outputs. Nothing is gathered between layers, and no GPU holds a full copy of the input, the activations or the weights.

## How easy it is to use

Jigsaw layers take the *global* (unsplit) sizes, plus the process groups of a mesh. Inside, they handle the halo exchanges, the ring communication and the gradient reductions. The training loop does not change.

### Convert an existing model

`convert_to_jigsaw` walks an ordinary PyTorch model and swaps every layer it knows (`nn.Linear`, `nn.Conv*`, `nn.ConvTranspose*`, `nn.LayerNorm`, `nn.GroupNorm`, `nn.Softmax`, attention and roll) for its distributed version. Each GPU keeps only its shard of the weights:

```python
import torch
import jigsaw
from jigsaw.convert import convert_to_jigsaw
from jigsaw.launch import init_cuda

device, *_ = init_cuda()                               # reads the SLURM or torchrun environment
mesh = jigsaw.make_process_mesh({"row": 2, "col": 2})  # tokens over "row", channels over "col"
torch.manual_seed(0)                                   # every rank starts from the same model
model = convert_to_jigsaw(MyViT(), mesh, device)       # ring attention over "row"

y = model(x)  # x: this GPU's shard, (batch, tokens / 2, channels / 2)
```

Elementwise layers such as activations and dropout are correct on a shard and are left alone. Layers that the converter cannot split safely, such as batch norm or pooling, raise an error instead of silently giving wrong results.

### Or write the model with Jigsaw layers

For full control, use the distributed layers directly. A CNN on an image split into a 2 × 2 grid of tiles:

```python
mesh = jigsaw.make_process_mesh({"sh": 2, "sw": 2, "col": 1})  # 4 GPUs: 2 x 2 tiles
spatial = (mesh["sh"], mesh["sw"])

def conv(cin, cout):
    return jigsaw.modules.DistributedConv2d(
        cin, cout, kernel_size=3, padding=1, device=device,
        spatial_group=spatial,       # exchanges halos with neighboring tiles
        channel_group=mesh["col"],
    )

model = torch.nn.Sequential(conv(3, 16), torch.nn.GELU(), conv(16, 3))
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
loss_fn = jigsaw.modules.DistributedMSELoss(reduce_groups=spatial)  # loss over the full image

for x, target in loader:   # each GPU loads only its tile
    loss = loss_fn(model(x), target)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
```

### Run it

```bash
torchrun --nproc-per-node 4 train.py     # one process per GPU
srun --ntasks-per-node=4 python train.py # or on a SLURM cluster
```

All layers also work on the CPU with PyTorch's `gloo` backend. The examples in the repository fall back to the CPU automatically when there are fewer GPUs than processes, so a distributed model can be debugged on a laptop before requesting cluster time.

Further features:

* **Data parallelism on top.** Add a `"dp"` axis to the mesh and wrap the model with `jigsaw.parallel.wrap_ddp`. It checks the setup and raises if the process group is wrong or if the replicated weights differ.
* **Leave again.** `reshard_parameters` moves a trained model to a different mesh, and `convert_to_torch` merges the shards back into plain PyTorch layers for inference or fine-tuning.
* **Checked against PyTorch.** The examples are tested in CI against their undistributed equivalents: values, loss and gradients.
* **Attention options.** Ring attention, Ulysses, or a hierarchical mix of both. Communication can overlap with computation on CUDA, and saved keys and values can be offloaded to CPU memory.

The [`examples/`](https://github.com/DeifiliaTo/Jigsaw/tree/main/examples) folder has short, runnable scripts: a domain-parallel CNN, a ViT, a Swin Transformer, data parallelism, a tiled dataloader, model conversion and resharding.

## Performance

### Long sequences

Splitting the sequence and the channels means that memory per GPU depends on the tile size, not on the image size. Larger images use more GPUs, not more memory per GPU.

**One attention layer on up to 1,024 GPUs.** Width 4,096, 32 heads and 65,536 tokens per GPU, on JUPITER's NVIDIA GH200 GPUs. Going from 4 to 1,024 GPUs, the global sequence grows from 256K to 67 million tokens.

* Jigsaw's memory-lean ring runs up to **67 million tokens at a constant 16–19 GB per GPU**. The sequence length is limited by the number of GPUs, not by GPU memory.
* The hierarchical ring with Ulysses inside each node drops only from 42% to 38% of peak between 2 and 256 nodes: **90% scaling efficiency**.

**One Transformer block on three GPU generations.** Attention and MLP on 32 GPUs, split 16 ways along the sequence and 2 ways along the channels, on NVIDIA A100, GH200 and GB200, from 128K to 4M tokens, for training and inference.

* Up to 40% of peak in training and 49% in inference on GH200, and 42% and 55% on GB200.
* CPU offloading of the saved keys and values costs less than 1% throughput, because the copies overlap with the attention computation.

**ViTs on global weather data.** We trained global-attention ViTs on ERA5 with 64,800 to 259,200 tokens and 25.7 to 404.9 million parameters, in bf16. The largest ran on 64 GH200 GPUs: 4 data-parallel copies × 8 spatial tiles × 2 channel groups. To our knowledge, this is the first ViT trained with global attention over the full 0.25° globe.

### Billion-parameter models

In the [arXiv preprint](https://arxiv.org/abs/2507.05753), we trained WeatherMixer, an MLP-based weather model with 1 to 2.4 billion parameters, on up to 256 NVIDIA A100 GPUs. With Jigsaw, the models reached **9 and 11 petaflops per second**, 23% and 28% of theoretical peak, at **68% and 72% scaling efficiency**. Data parallelism alone reached 51%.

### NVIDIA and AMD at full-machine scale

Jigsaw is the domain–tensor part of [BEAST]({{ base_path }}/blog/2026/09/beast-4d-parallelism/), a Bayesian Swin Transformer for global weather forecasting. In BEAST, Jigsaw splits each model copy across 8 GPUs (4 tiles × 2 channel groups). Data- and uncertainty-parallel copies of that model provide the rest of the scale.

* **JUPITER** (Forschungszentrum Jülich, NVIDIA GH200): **3.96 exaflops per second** peak on 20,480 GPUs, with a 2.4-billion-parameter model.
* **LUMI** (CSC, AMD MI250X): **463 petaflops per second** on 1,024 nodes (4,096 GPUs), at 92% strong-scaling efficiency, with a 1.1-billion-parameter model.

The code is the same on both machines. AMD's RCCL registers under the same name as NVIDIA's NCCL in ROCm builds of PyTorch, and Jigsaw needs no vendor-specific code paths.

## Limitations

* **Small scale.** The memory-lean ring uses fixed-size buffers, so it needs 16–19 GB per GPU even on a single node. For small problems, keeping all key/value blocks is faster.
* **Layer coverage.** Not every PyTorch layer has a distributed version. Batch norm, pooling, upsampling, embeddings and `nn.MultiheadAttention` are not supported. `DistributedLinear` supports splits of 1, 2, 4 or 8 GPUs per model copy.
* **Precision.** Mixed precision is limited to fp16 and bf16; FP8 is not supported.
* **Launchers.** Large runs have only been tested with SLURM. `torchrun` works but has not been tested at scale.

## Getting started

```bash
git clone https://github.com/DeifiliaTo/Jigsaw && cd Jigsaw
pip install -e .
torchrun --nproc-per-node 4 examples/domain_parallel.py
```

Requirements are Python 3.11 or newer, PyTorch 2.8 or newer, `einops` and `numpy`. Start with [`examples/domain_parallel.py`](https://github.com/DeifiliaTo/Jigsaw/blob/main/examples/domain_parallel.py), then [`examples/vit.py`](https://github.com/DeifiliaTo/Jigsaw/blob/main/examples/vit.py).
